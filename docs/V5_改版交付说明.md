### 图1 那个异常的真实根因（已修，非掩盖）
异常原文：
```
PlatformException(The Activity class declared in your AndroidManifest.xml
is wrong or has not provided the correct FlutterEngine...)
```
根因是**三处独立错误叠加**，只修一处不够：

1. **`MainActivity` 基类错误**。`audio_service` 0.18.15 在
   `AudioServicePlugin.onAttachedToEngine` 里这样判定：
   `wrongEngineDetected = flutterPluginBinding.binaryMessenger !=
   getFlutterEngine(activity).dartExecutor`。
   原来的 `MainActivity : FlutterActivity` 走的是**自建引擎**，
   插件绑定用的却是另一个引擎 → 判定为不等 → 之后**每一次**
   MethodChannel 调用都抛上面那个异常（`PlaybackHandler` 的传输方法全走该通道）。
   **修法：`class MainActivity : AudioServiceActivity()`**。
2. **Manifest 里 service 类名写的是 0.17 时代的 `MediaPlaybackService`**，
   0.18.x 里这个类不存在 → 必须改成
   `com.ryanheise.audioservice.AudioService`。
3. **缺少 `MediaButtonReceiver`** → 遥控媒体键收不到广播。

结果：这三处一起修掉后，异常不再出现；**不是把异常藏起来**。

### 待真机验证
- 电视上「点开 App → 首页」全程无异常（需看诊断页确认无
  `wrongEngineDetected` 相关记录）。

## 三、歌曲风格归纳（§三 / §三-A / §三-B）

### 根因
实测曲库里 `Track.genres` **全是空数组**，而 V4 的风格页只读这个字段
→ 风格页永远停在「暂无风格标签」的空态，功能等于不存在。

### 做了什么
- `lib/domain/genre.dart`：`GenreRules`（`version = 1`）+ 统一风格集合
  **11 类 + `待分类`** + 约 200 条别名映射 + 版本词表。
  ⚠️ `genresFromText` 是**按词匹配**的：拉丁词要求**整词精确**
  （否则 `Rocket Man` 会被判成摇滚、`Ghost` 判成原声带、`Brand New` 判成 R&B），
  CJK 允许子串（中文没有词间空格）。
- `lib/domain/genre_inferencer.dart`：四级优先级 + 置信度 + 来源：
  `a 手动确认 → b 显式标签 → d1 专辑内一致 → d2 标题词 → d3 同歌手常见`。
  每个结论都带 `GenreSource`（`manual` / `serverTag` / `albumRule` /
  `titleRule` / `artistRule`）与 `confidence`，**绝不把推断冒充原始标签**。
- **「待分类」是带真实曲目列表的一等桶**（用户点进去能看到是哪些歌、
  可以手动指定），不是「未知风格」这种伪造分类，也**不会**把无标签的歌
  默认算成「流行」。
- 概览页对**整类都由推断得出**的风格显示「推断」徽标
  （只要有一首是原始标签或用户确认，就不整类标记）。
- 手动确认存**独立文件** `genre_overrides.json`，
  **重建索引永不动它**（§三-B.7）。

### 验收（`test/genre_inference_test.dart`，19 例）
标签映射（含多风格 `Synthpop → 流行+电子`）、版本词不得当风格、
`Rocket/Ghost/Brand New` 不误判、语言与歌手姓名不参与判定、
专辑传播阈值（2 首一致才传播）、歌手阈值（3 首）、
手动确认优先级最高、待分类桶、`inferred` 标记。

### 待真机验证
真实曲库（2796 首）归纳后的「待分类」比例与人工抽检正确率 ——
这需要连上用户的 NAS 才能评。

## 三-A / 三-B、全曲库索引与记忆（关键根因）

### 根因（图4 的直接原因）
实机现象：**刚启动时歌手/专辑不全；点开「音乐库」并让它扫到全部音乐后，
分类就恢复正常。**

代码层面的根因非常直接：概览页读的是 `library.tracks`，而它只包含
「**用户滚动过的那几页**」——
`app_shell` 启动只 `loadFirst()`（50 首），只有 `song_list_page` 滚到底
才 `loadMore()`，`buildFullIndex()` 唯一调用点在 `search_page`。
于是不点音乐库 → 永远只有 50 首参与分组，而首页卡片显示的
服务端 `total` 是 2796 —— **两个口径天生对不上**。

### 做了什么
`LibraryRepository` 重写成**完整曲库索引服务**：

1. **与页面无关**：登录恢复后立即 `startSync()`，不要求用户先打开音乐库；
2. **缓存优先**：启动先读本地索引 → **立刻**有完整歌手/专辑/风格，
   再后台核对增删改；
3. **分页拉全**：按契约 `page` + `size` 逐页取，直到 `hasMore == false`
   或数量与 `total` 一致；不靠把 pageSize 调大；
4. **按稳定 `guid` 去重**，检测重复页 / 空页 / 总数漂移（漂移则自动重扫一次）；
5. **半成品不覆盖成品**：分页失败保留上一次完整索引；
   如果手上那份本来就是完整的，就**继续标记为完整**
   （只是「本次在线核对」没做完），否则用户明明看着完整列表却被提示
   「曲库未整理完成」；
6. **绝不碰播放队列**：后台整理**不调用** `onPageLoaded`
   （那是「播放到队尾续页」的钩子），不会把整个曲库塞进当前队列；
7. **落盘**：`lib/services/catalogue_store.dart`，应用私有目录下的普通 JSON
   （走 `feiniu/boot` 新增的 `dataDir`，**不引 `path_provider`**，
   也不塞进 `flutter_secure_storage` —— 那会让启动卡顿）；
   原子写 = `.tmp` + `flush` + `rename`；schema / identity 不符直接丢弃；
8. **手动重建**：诊断页有「重建曲库索引」按钮，语义是后台扫完再原子切换。

### 验收（`test/catalogue_index_test.dart`，11 例）
**137 首 / 每页 50 首**的场景：
- `startSync` 自己把三页拉完（`1/50, 2/50, 3/50`），不依赖任何页面；
- **第 51 / 101 / 137 首**都出现在正确的歌手与专辑分组里
  （这正是「只对前 50 首分组」时会失败的断言）；
- 服务端返回重复项时按 guid 去重，统计不虚高；
- 某页失败：保留已取得的数据且**不谎报「已整理完成」**；
- 半成品不覆盖上一次完整索引；
- 重启后直接读本地索引拿到全部分类（离线也能读回 137 首）；
- 索引**按身份分文件**：换账户不串数据、也不互相覆盖；
- 曲库新增曲目后再次整理能核对出来；
- 损坏的索引文件按「无缓存」处理，不阻断启动；
- 手动风格覆盖与索引分离，重建索引不会清掉用户确认。

### 重启后的验收路径（需求要求的那条）
`整理完 → 完全退出 → 重启 → 不打开音乐库` → 首页/歌手/专辑/风格
**直接显示完整统计**。这条路径由上面的「重启后直接读本地索引」用例覆盖
（离线也能读回全量），真机上按此步骤走一遍即可。

## 四 / 四-A、布局与网格

### 根因（图4「一屏两张巨卡」）
Android TV 盒子在 1080p 面板上通常上报 **`density = 2.0`**，
也就是 Flutter 侧只有 **960×540 逻辑像素**，不是 1920×1080。
按 1920 逻辑宽标定的最小瓦片宽 250 + 间距 18 →
可用宽 ≈ 714 → `floor(714 / 266) = 2` 列。

**修法**：按电视**实际逻辑视口**标定阈值：
- 瓦片最小宽 250 → **150**，间距 18 → **12**，列数 `clamp(3, 6)`；
- 960 宽 → 4 列；1280 宽 → 6 列；1920 宽 → 上限 6 列。
- 网格行高**由瓦片宽度反推**（封面色块 + 文字块 + 余量），
  不写死 —— 写死会导致宽屏上封面变大而溢出行高。

### 其他布局项
- 封面统一正方形、文字显式 `height`（见下）、不溢出；
- 迷你播放器降高（86 → 72）但**保留五段交互**：
  `封面 → 上一首 → 播放暂停 → 下一首 → 队列`，并新增只读模式标识；
- 正文高度扣除底部迷你播放器（在 `Column` 里占位，不做 `Stack` 叠加）；
- 焦点项在列表/网格内自动完整滚动到可见区；
- 专辑分组按**稳定标识**（`al:<guid>`，名字 + 首位歌手兜底）——
  ⚠️ 只按专辑名分组会**误合并同名专辑**（不同歌手的同名专辑很常见）。

### ⚠️ 一个必须记住的坑：固定行高里的文字必然溢出
M3 主题给 `DefaultTextStyle` 的默认行高是 **1.43**，`TextStyle` 会与它
**merge** → `fontSize: 21` 实际占 30px 而不是 25px。固定高度行
（`itemExtent` / `mainAxisExtent`）里放「大标题 + 小副标题」的 Column
必然 `RenderFlex overflowed`（电视上就是黄黑条纹）。
**更隐蔽的一层**：Flutter 把**每一行**行盒高度**向上取整**，所以
「字号 × height」必须是**整数**（`19 × 1.2 = 22.8 → 23`），
否则会出现 `overflowed by 0.400 pixels` —— 写了 `height` 也照样红，
肉眼完全看不出来。
因此本项目所有固定行高内的 `Text` 都显式写 `height`，
并统一用乘积为整数的组合（×1.2 配 20/15/25，×1.25 配 20/24）。

### 待真机验证
1920×1080 与 1280×720 两种分辨率下的实际列数与是否出现黄黑条纹。
（本机无法渲染，只能靠 `LayoutBuilder` 的算式推定。）

## 六、歌词链路

### 根因（图5「只有一个 ♪」）
`LyricRepository` 里判断「NAS 有没有歌词」用的是 `nasDoc.isNotEmpty`：
NAS 的 `lyric/list` 返回**非空 list、但内容只是 `♪` / 空白 / 只有时间标签**时，
判据成立 → **提前 return → 在线兜底永远不执行**，
界面上就只剩一个音乐符号。

### 做了什么
- `LyricDoc` 新增 `informativeCharCount()` 与 `isUsable`：
  去掉时间标签后，只统计**有信息量的字符**（汉字 / 字母 / 数字），
  全部行合计 **≥ 4** 才算有效。
  `♪♪♪` → 0 → 无效；`[00:12.00]` → 0 → 无效；
  `纯音乐，请欣赏` → 6 → 有效（这确实是服务端给的告知）。
- `LyricRepository`：判据从 `isNotEmpty` 改成 `isUsable`；
  **在线候选**与**自动绑定**同样要求「有效」；
  诊断里区分「NAS 无有效歌词」与「NAS 请求失败」。
- 歌词视图：只有整篇确实有文字行时，才把空行画成 `♪`
  （否则整篇空行会画出一串音乐符号）。
- 其余 V4 已有并保留：`正在查找歌词` / `暂无歌词` / `获取失败可重试` 三态、
  在线候选列表（置信度不足时**只给候选不自动绑定**）、
  `OnlineLyricMatcher` 版本/时长感知打分、手动选择持久化。

### 验收（`test/lyric_usability_test.dart`，12 例）
占位符判定、**NAS 占位符必须触发在线兜底**（这条就是图5 的回归）、
NAS 有效则**不联网**、在线候选只有占位符时不绑定、缓存命中的无效歌词不复用。

### 待真机验证
- 真实 NAS 上 `lyric/list` 到底返回什么形态（本机没有 NAS 凭据，
  V4 的契约文档里也没有歌词样本）；
- 在线兜底（`https://lrclib.net/api`）在用户所在网络是否可达
  —— 境外服务在国内部分电视网络下不可达，因此在设置里留了开关，
  关掉只影响歌词，不影响任何其它功能。

## 七、手机扫码遥控电视

### 架构
```
手机浏览器 ──HTTP/WS──▶ 电视端 RemoteControlServer（lib/services/remote/）
                          ├─ GET  /              内置手机网页（零 CDN）
                          ├─ POST /api/pair      配对码 → 会话凭证
                          ├─ GET  /api/state     当前状态
                          ├─ POST /api/cmd       播放控制 / 浏览 / 搜索
                          ├─ GET  /api/cover     封面代理（电视转发字节）
                          └─ GET  /ws            实时状态推送 + 命令应答
                                   │
                                   ▼
                        PlaybackRepository / PlaybackControl（**同一份队列**）
```
- **不建第二套队列**：所有命令翻译成 `PlaybackControl` 调用，
  与遥控器、迷你播放器、全屏播放器、系统媒体键走的是同一份状态。
- **手机不播音频**：不下发音频 URL；封面由**电视代理**获取后转发字节，
  因此手机端**拿不到任何 NAS 凭据**。
- `lib/services/remote/qr_code.dart`：**自写**离线二维码编码器
  （固定版本 4-L、字节模式、单块无交织、格式信息用 BCH(15,5) 现算），
  避免引入 `qr_flutter` 依赖，也让「扫不出来」这件事可控。
- `lib/ui/widgets/qr_view.dart` + `lib/ui/pages/remote_control_page.dart`：
  电视端页面提供**三重兜底** —— 二维码 / 配对码大字 / 可选择的完整地址。

### 安全
- 配对码 6 位、一次性、5 分钟有效、字符集去掉易混的 `0 O 1 I L`；
- 会话凭证 32 位随机、12 小时有效、**单会话**（新配对顶掉旧的）、
  可随时撤销、**不落盘、绝不写日志**；
- 二维码里只放 `http://<电视IP>:<端口>/#<配对码>`（用 fragment，
  **不会出现在 HTTP 请求里**，因此也不会进服务端访问日志）；
- 命令带自增 `id` 去重（弱网重发不会连切两首）；
- 请求体大小上限、路径白名单、`x-frame-options: SAMEORIGIN`；
- 退出登录 / 关闭服务即刻失效（`stop()` 会 revoke 会话）。

### 验收（`test/remote_pairing_test.dart`，17 例）
配对码一次性/过期/字符集、凭证校验与撤销、单会话替换、命令去重、
会话标签裁剪、二维码内容不含任何凭据、二维码**结构**
（33×33、三角定位图案、时序图案、暗模块、格式信息两副本一致）
以及**纠错码字的数学正确性**（码字多项式在生成多项式 20 个根上求值为 0 ——
这是 Reed–Solomon 正确的充要条件）。

### ⚠️ 待真机验证（**这一项最需要真机**）
- 手机相机能否真的扫出这个二维码（自写编码器只保证结构与 RS 正确，
  「能扫」还涉及打印/显示尺寸、对比度、电视屏幕反光）；
- 手机网页在低版本手机浏览器上的表现；
- 电视与手机在同一局域网内的连通性（部分路由器 AP 隔离会挡住）。

## 八、拼音模糊搜索（本轮最后一份任务书）

### 拼音库选型
选 **`pinyin: ^3.3.0`**。原因：
- `lpinyin` 2.0.3 的 SDK 约束是 `>=2.12.0-259.9.beta <3.0.0`，
  **不含 Dart 3**，pub 解析会直接失败
  （pub.dev 页面上显示的 "Dart 3 compatible" 是误导）；
- `pinyin` 3.3.0 约束是 `>=2.12.0 <4.0.0`，纯 Dart、零依赖、BSD-2，
  且内置 1.1MB 字表 + 1.3MB 词组表 —— 正是「多音字按词组判定」所需的。

⚠️ 顺带一个真实的 API 陷阱：`PinyinHelper.minPhraseLength` /
`maxPhraseLength` 在 3.3.0 里是**可空的 `int?`**，
而旧名 `minMultiLength` / `maxMultiLength` 已被标记废弃
（本项目 analyzer 的 info 也判失败）。两条路都不能直接走。

**处理方式**：词组最长匹配本来就是我们自己遍历 `PinyinHelper.phraseMap`
实现的，所以**自己量一遍词组表**（最短/最长词组字数，一次性、毫秒级），
彻底不碰库的全局开关 —— 也不会出现「库的开关被改、匹配窗口没跟着改」的漂移。

### 多音字处理
- 项目词典 `lib/domain/pinyin_lexicon.dart`（约 150 条）覆盖
  **姓氏**（`单依纯 = shan,yi,chun`、`曾轶可 = zeng,yi,ke`、`那英`、`朴树`…）、
  **地名**（`重庆 = chong,qing`、`长沙`、`厦门`、`蚌埠`…）、
  **音乐场景**（`音乐 = yin,yue`、`乐队 = yue,dui`、`单曲 = dan,qu`…）、
  **通用多音字词组**（`重要`、`重新`、`行走`、`银行`…）与常见歌名。
- 不做「每个字展开所有读音」——那会让索引爆炸且引入大量假命中。
  词组不命中时退回单字常见读音；**无法确定就保留中文搜索，不编造命中**。
- 词典由测试钉住四条约束：简体、全小写无调、`ü` 写成 `v`、
  **读音个数必须等于字数**（对不上时整条忽略并退回逐字，
  绝不让一条写错的词典把整首歌的索引错位）。

### 匹配模型：逐字对齐 + 回溯（这是关键设计）
`AlignedText` 保存**逐字**的音节与首字母（不是只存整串），
于是「每个字可以用四种方式消费查询」变成一个纯粹的字符串推进问题：
汉字原位 / 整音节 / 音节前缀 / 首字母。
带回溯的 DFS + `(文档位置, 查询位置)` 失败记忆化，最坏 `O(L×Q)`。

这一层是**中英混合查询能成立的前提**：
`周jl`、`jie伦`、`Jay周杰伦` 既不是原文的子串、也不是整串拼音的子串，
只存整串的实现必然搜不到。

### 需求逐条对照
| 需求 | 实现 |
|---|---|
| ① 中文原文 | 汉字原位匹配，优先级最高 |
| ② 全拼（含空格） | `zhoujielun` / `zhou jie lun` → 周杰伦 |
| ③ 首字母（含前缀） | `zjl` / `zj` → 周杰伦；完整首字母分值更高 |
| ④ 部分拼音 | `zhoujie` / `jielun` / `qingt` |
| ⑤ 混合查询 | `周jie伦`、多关键词 AND（可跨歌名/歌手/专辑字段） |
| ⑥ 英文大小写 | 归一化折叠，`GET LUCKY` = `get lucky` |
| ⑦ 空格/全半角/标点 | 归一化时丢弃，**但绝不改写展示用原文**，版本词（Live/Remastered）保留 |
| ⑧ 轻微拼错 | 编辑距离 ≤1（**含相邻换位**，`zhoujielnu`），
只对长度 ≥4 的查询、且正常结果少于 3 条时启用，分数远低于精确命中 |

### 排序
`强度基数 + 位置基数 + 字段加成`：
- 强度：原文 900 > 拼音 600 > 首字母 400 > 模糊 200；
- 位置：完全 100 > 前缀 50 > 包含 0；
- 字段：歌名 40 > 歌手 25 > 专辑 10。

级差远大于加成，因此「同强度内先比位置、再比字段」永远成立，
不会出现「歌手完全匹配压过歌名完全匹配」的反直觉结果。
最终 tiebreak 是**曲库原始顺序**，因此同一查询结果完全可复现
（需求禁止「每输入一个字母就无规律跳动」）。

### 完整曲库、缓存与性能
- 搜索基于 `LibraryRepository` 的**同一批 `Track` 对象**，
  **不另建数据源**（需求 §6 明令禁止）；电视端与手机遥控共用同一个
  `SearchService`（手机侧不再有第二份小索引）。
- 拼音索引持久缓存 `lib/services/search_index_store.dart`：
  与曲库索引**分开两个文件**（两者的失效条件不同 ——
  归一化规则/拼音库/词典的版本一变，拼音键整份作废，
  但不该连累曲目元数据；反之曲库刷新也不该覆盖检索键）；
  文件名含身份摘要 → 账号/服务器隔离；
  版本指纹不符 → **整份丢弃重建**，绝不沿用失效缓存；
  任何读取异常 → 按「无缓存」降级，**绝不清空已有可搜数据**。
- 增量维护：指纹 = 标题 / 歌手 / 专辑 / 更新时间；
  指纹没变的条目**直接复用上次的音节表**（缓存的意义就在于不重跑拼音转换）。
- 不阻塞：分片构建（160 首/片），片间 `await` 让出事件循环。
  **这里刻意没用 isolate** —— `pinyin` 的字表/词组表是 2MB 级 Dart 常量，
  spawn 新 isolate 会再加载一遍（电视盒子内存不宽裕），
  而真正的诉求是「不卡住播放和界面」，分片让出能更省地达到同一效果，
  行为也完全可预测、可测试。
- 防过期：`SearchService.search()` 返回带**序号**的结果，
  UI 只采纳序号更大的那个；晚到的旧结果直接丢弃。
- 防抖：搜索页 220ms（需求区间 150–300ms）。

### 验收（`test/pinyin_search_test.dart`，24 例）
覆盖需求 §二/§三/§四/§五 的每一条：八种输入形态、多音字词组优先
（`chongqing` 命中「重庆森林」而 `zhongqing` 不命中）、
无结果不编造、排序（原文精确 > 拼音；歌名命中优先）、稳定可复现、
结果不含内部拼音索引、**137 首场景下第 51 首与最后一首都能被拼音找到**、
持久缓存 + 账户隔离 + 版本不符整份重建 + 曲库清空后能恢复、
查询序号（晚到的旧结果被标记过期）、归一化规则与项目词典的四条约束。

### 待真机验证
- 电视遥控器**输入字母**（虚拟键盘/拼音输入）的实际体验；
- 结果列表的焦点移动与大曲库下的滚动手感；

  这个数字**必须实测**，本机无法测。

## 九、四种播放模式（补充任务书）

### 明确规则（优先于此前含糊的「循环」描述）
按钮顺序 = 枚举顺序：`顺序播放 → 列表循环 → 随机播放 → 单曲循环 → 顺序播放`。

| 模式 | 自然结束 | 手动下一首 | 手动上一首 |
|---|---|---|---|
| **顺序播放** | 有下一首就去，最后一首**停住不回第一首** | 同上；末首不重新开始整队列 | 回前一条目（首曲不回绕） |
| **列表循环** | 最后一首 → 第一首 | 同上，队尾回绕 | 第一首 → 最后一首 |
| **随机播放** | 走**同一份随机计划** | 同左（**同一计划**，不重新洗牌） | 沿**实际播放历史**回退 |
| **单曲循环** | 从 0 秒**重新下发加载**同一首，持续循环 | 切到队列正常顺序的下一首，**仍保持单曲循环** | 同上，可回绕 |

### 关键实现点
- **真实随机**：以 `guid` 为身份的 Fisher–Yates 遍历计划 + 游标 + 历史。
  绝不用下标（增删会漂移）、绝不用标题（会重名）。
  一轮内不重复；一轮走完重新洗牌，且排除当前曲以避免跨轮立即重复。
  「上一首」= 回放历史里**真实播过**的条目，不是列表 `_index - 1`。
- **统一由应用层决定循环/随机**：底层（ExoPlayer / `LoopMode`）保持 `off`。
  `PlaybackHandler` 覆盖的 `setRepeatMode` / `setShuffleMode` **刻意空实现**，
  避免「底层 repeat-one 与应用自动下一首同时生效 → 两边各洗一次牌」。
- **单曲循环不用 `seek(0)+play()`**：completed 态下不可靠
  （要么不响，要么立刻又判到边沿）。改为复用「重新下发加载」的串行链。
- **`completed` 判边沿**：只在「非 completed → completed」跃迁派发一次
  自动下一首，避免连续跳曲。
- **切换模式不重启歌曲、不重建音源、不丢进度**；
  暂停时切换保持暂停；随机顺序/游标/历史随队列保存，
  重启后不会无提示变回顺序播放；不同账号/服务器隔离。
- 电视端与手机端四个 UI 入口（迷你播放器 / 全屏播放器 / 队列面板 /
  手机遥控）显示的是**同一个状态对象**，因此显示与实际必然一致。

### 验收（`test/playback_mode_test.dart`，含可控随机种子）
模式循环顺序、顺序播放的四个边界、列表循环两轮、
随机（5 个种子至少 3 种不同顺序 / 手动与自然结束同计划 / 跨轮不重复 /
历史回退 / 无历史不乱跳）、单曲循环（重载而非 seek / 手动切歌保模式 /
队尾回绕 / 不堆历史）、模式切换生命周期、并发重入、
空队列/1 首/2 首/重复条目/137 首/追加/移除、统一入口与偏好持久化。

### 那些「看起来像随机坏了」的现象，其实各有明确原因
1. **`Random.nextInt` 是有放回取样** —— 50 首时约 9 次就会撞到重复，
   这不是 bug 而是数学；所以改成「洗牌后依次取出」。
2. **队列当时只有 50 首** —— 首页只加载了一页，随机当然只在 50 首里转。
   `SearchService` / 各页「随机播放」入口现在都会先建立该入口对应的**完整队列**。
3. **队尾不触发预加载** → 最后一首之后无从可去。
4. `seek(0)+play()` 在 completed 态不可靠。
5. 随机「上一首」走的是列表下标，而不是实际播放历史。
