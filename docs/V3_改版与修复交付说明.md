## 2. 「测试版界面」的根因与修复

**根因**：登录流程原本是**三段式**
`login → status → shell`，中间那一段 `status` 就是 `ServerStatusPage` ——
一个显示**原始 JSON**（`{"initialized": true}`）加一个「进入歌曲列表」按钮的调试页。
它当初是为了排查电视端连不上 NAS 才加的，功能修好后**没有摘掉**，
于是成了用户每次登录都要点一下的「测试版界面」。

**修复**：
- 直接**删除**该页面文件；
- `AppFlow` 的 `Stage` 枚举收敛为 `login` / `shell` 两态；
- 「进首页还是进登录页」的判定**唯一化**到 `AuthRepository.isLoggedIn`
  （它由 `restore()` 从安全存储恢复会话后置位），`initState` 里已登录就直接
  `Stage.shell`，不再有任何中间态。

**安全边界没有被放松**：会话恢复走的是原有的 `SecureStore` 路径；
`tokenExpired`(99999/401) 与 `auth`(120001) 的语义区分、登出清会话、
明文密码永不出本机（只存 `SHA256` 小写 hex）全部保持原样。

## 3. 歌词「不显示 / 不同步」的根因与修复

一共查出**三个**独立问题，不是一个：

### 3.1 滚动完全没实现（这是「不跟随」的主因）

旧 `LyricView` **只有高亮下标的变化，没有任何滚动逻辑** ——
歌词列表构建出来后，视口**永远停在最上面几行**。
于是不管播到第几句，屏幕上显示的始终是第一句附近的文字，用户看到的就是
「歌词不显示 / 不同步」。

**修复**：加 `ScrollController`，每 400ms 刷新时把当前句**居中**
（列表上下各留 `(视口高 - 行高)/2` 的 padding，所以「第 i 行居中」= 滚到 `i × 行高`，
已经在位就不动，避免抖动）；换歌时用 `docEpoch` 识别出「内容被整份替换」，
把视口 `jumpTo(0)` 弹回顶部。

### 3.2 切歌后残留上一首的歌词

`load()` 在**请求返回之后**才替换 `_doc`，所以「按下下一首」到「新歌词回来」
这段窗口里，界面上显示的**仍然是上一首的歌词**。

**修复**：`load()` 未命中缓存时，**先**把 `_doc` 清空并自增 `docEpoch` 再发请求。

### 3.3 高亮行定位会漏判

`activeLineIndex` 原本用二分查找，前提是「`time == null` 的行一定连续排在前面」。
但 `parseLrc` 里无时间轴的行是按 `Duration.zero` 参与排序的，
它与真正的 `[00:00.00]` 行**先后顺序不确定** —— 二分一踩到 `null` 就往前半区收缩，
于是漏掉合法行，表现为「高亮跳错句 / 停在第一句不动」。

**修复**：改为线性扫描（取最后一个 `time <= position` 的行）。
歌词只有几百行、每 500ms 才算一次，线性完全够用，且对「有空行 / 有 offset /
顺序不完美」天然正确。

### 附带的两个加固

- **12 秒硬超时**：Dio 的 `receiveTimeout` 只约束**两个数据包之间的间隔**，
  服务端持续吐字节但永不结束时**不会触发**。电视上没有 adb，
  「歌词区永远转圈」和「这首没歌词」在屏幕上长得一样，必须靠超时区分。
- **超时/异常一律降级为「暂无歌词」**，绝不影响播放与遥控器。

### 歌词区不参与焦点链

`LyricView` 整块用 `ExcludeFocus` 包裹。
另外它的自动滚动与刷新**不会让播放控制按钮失焦** ——
因为 `LyricView` 只 `select` 歌词状态，控制区只 `select` `isPlaying` / `mode`，
两者互不触发重建（播放页的 `build` 也**不订阅进度**）。

## 4. 「进入进度 / 快进快退区后无法返回」的根因与修复

**根因有两条，叠加在一起**：

1. `_ProgressSection` 把 `Shortcuts` / `Actions` 放在 `Focus` 的**外层** ——
   方向键的处理路径分裂成两条：外层 `Shortcuts` 先吃、`Focus` 树再走一遍，
   结果是「按上键有时回得去、有时回不去」。
2. Material 的 `Slider` **自身就是一个可获焦节点，并且会消费左右方向键**。
   一旦焦点落到进度条内部，左右键被它吃掉、上下键找不到出口 ——
   这就是**「只能进去，出不来，只能按 BACK 退出整个播放器」**的直接原因。

**修复**（不是给单个控件补属性，而是重建整页的焦点导航）：

- 三层焦点链全部用 `TvFocus` 的 `nextUp / nextDown / nextLeft / nextRight`
  **显式指定目标节点**，完全不依赖 Flutter 的「就近寻找」启发式；
- 进度行**整行只留一个焦点节点**，`Slider` 包在 `ExcludeFocus` 里：

| 键 | 作用 |
|---|---|
| ← / → | 快退 / 快进 **5 秒**（这是需求里「明确设计的进度操作情形」） |
| OK / Enter / DPAD_CENTER | 等价于播放 / 暂停 |
| ↑ | 回**播放/暂停**按钮（优先回该按钮） |
| ↓ | 指回自己 = **原地不动** |

> ↓ 显式写成「自己」而不是留空，是为了避免框架的方向遍历把焦点甩到某个
> 不可预期的节点上 —— 那正是「按 ↓ 焦点就不见了」的来源。

- **不存在任何只进不出的死区**：进度区是最下一层，↑ 恒可达控制区。

## 5. 「上一首 / 播放暂停 / 下一首 选不中」的根因与修复

**根因**：旧 `_RoundButton` 的结构是

```
Tooltip > Focus(focusNode: _node) > Builder > ElevatedButton(...)
```

`ElevatedButton` **内部自己还有一个 `FocusNode`**。于是同一个按钮上有两个焦点节点：

- 焦点落在**外层**节点 → **高亮出现了，但按 OK 什么都不会发生**（外层没有 onPressed）；
- 焦点落在**内层**（按钮自己的）节点 → **按 OK 有效，但外层拿不到 hasFocus，
  于是没有任何视觉反馈**。

谁被选中取决于遍历顺序，表现就是**「时好时坏、随机失灵」**。
这同时也是第 6 节「焦点视觉反馈不稳定」的根因。

**修复**：新增 `TvFocus` —— 全程**只创建一个 `FocusNode`**，
把「焦点移动 / OK 激活 / 按下态」全都在同一个节点上处理：

```
TvFocus > Focus(单节点, onKeyEvent) > Builder > TvFocusRing(纯 Container + Icon)
```

**不再使用** `ElevatedButton` / `IconButton` / `ListTile` / `InkWell` 作为可聚焦控件。

`TvFocusRing` 的焦点视觉用**描边 + 底色 + 轻外发光**，
刻意**不用 `Transform.scale`** —— 放大一定溢出父容器，会被 `ListView` / `ClipRRect`
裁掉一半，或把相邻控件挤变形。描边由 `BoxDecoration.border` 绘制，完全落在自身
bounds 内，任何父级裁切都吃不掉它；未聚焦时保留**同宽度透明描边**避免布局跳动。
`focused` 与 `pressed` 是两个独立状态，遥控器按下去有独立的瞬时反馈。

## 6. 当前焦点导航路径

```
┌─ 第一层 · 顶部功能 ─────────────────────────────────────────┐
│   [返回 ⌄]                                        [列表循环 ▸] │
│      │ nextDown → 上一首                    nextDown → 下一首 │
└──────┼──────────────────────────────────────────────┼───────┘
       ▼                                              ▼
┌─ 第二层 · 核心播放控制 ─────────────────────────────────────┐
│              [上一首]   [播放/暂停]   [下一首]                │
│                 ↕           ↕            ↕                   │
│         nextDown    nextDown      nextDown                   │
└─────────────────┼───────────┼──────────────┼────────────────┘
                  ▼           ▼              ▼
┌─ 第三层 · 进度 / 快进快退（组合控件，整行一个节点）──────────────┐
│   ⏪5秒   0:42  ══════●════════  3:00  5秒⏩                  │
│   ← → = 快退/快进 5 秒 · OK = 播放暂停 · ↑ = 回播放/暂停       │
│                              ↓ = 原地不动                     │
└──────────────────────────────────────────────────────────────┘
```

- **横向**：`上一首 ←→ 播放/暂停 ←→ 下一首`，反向同理；
  两端做了**环形连接**（`上一首 ← 下一首`、`下一首 → 上一首`），
  所以左右永远有去有回，不会「到头了按不动」。
- **纵向**：顶部 ↓ → 控制区；控制区 ↓ → 进度区；↑ 原路返回（进度区 ↑ 优先回**播放/暂停**）。
- 进入播放页时焦点**直接落在「播放/暂停」**上（显式 `requestFocus`，不依赖 autofocus）。
- **切歌 / 播放暂停 / 歌词刷新后焦点都留在原按钮**：控制按钮用外部持有的
  `FocusNode`，重建时 `identical` 判定通过，节点不会被换掉。

## 7. 歌词数据从哪里来、怎么解析、怎么与进度同步

- **接口**：`GET /lyric/list?trackGUID=<guid>`
  （参数名是 **`trackGUID`**，大写 GUID；写成 `trackGuid` 会被服务端当作参数错误）。
  返回 `{ list: [...], preferred: ... }`，单条含 `text` / `time` / `duration` / `offset`。
- **只加载当前一首**：歌词接口按单曲查询，绝不全库拉取；带 20 条小缓存，
  来回切歌不会反复打服务端（`force: true` 供手动重试）。
- **解析**：`LyricDoc.parseLrc` 支持 `[mm:ss.ff]` / `[mm:ss:ff]` / 一行多标签 /
  文档级 `[offset:]`；非 LRC 的单条歌词按 `time`（**秒**）换算成 `Duration`。
  纯文本、空值、解析失败一律降级为「暂无歌词」，不抛异常。
- **与进度同步**：`LyricView` 每 **400ms** 读一次 `PlaybackRepository.position`，
  算 `activeLineIndex`，变化时才更新高亮并把该句滚到居中。
  快进 / 快退 / 拖动进度条之后位置立刻变，下一次刷新（≤400ms）就同步过去；
  拖动过程本身**不产生播放请求**（只在 `onChangeEnd` 时 seek）。
- **换歌**：`PlayerPage` 监听 `PlaybackRepository`，一检测到 guid 变化就
  `lyrics.load(新歌)`；`LyricRepository` 用 `_requestSeq` 保证
  **慢的旧请求回来也不会覆盖新歌**，并用 `_docEpoch` 让 UI 把视口弹回顶部。
