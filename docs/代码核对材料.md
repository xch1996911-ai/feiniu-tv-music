## 5. 故障定位：已证实 vs 推测

### 5.1 在线歌词没有显示

**已证实（读代码即可确认，不需要真机）**
1. 在线源**已接入**，不是「忘了注入」：`boot_screen.dart:172`
   `LyricRepository(music, online: LrclibLyricSource())`；
   总开关 `LyricRepository.onlineEnabled = true`（`lyric_repository.dart:70`）。
2. NAS 的占位符（只有 `♪`/空白/只有时间标签）**已经不会**阻断在线兜底：
   判据是 `isUsable`（:212），无效时记诊断并继续（:220）。
3. **置信度不足时不会自动显示歌词**（`acceptThreshold = 0.7`，:271），
   只填候选（:284）。这是**刻意设计**，但它会让用户看到「暂无歌词」。
4. 视图在 `doc.isEmpty` 时无条件显示「暂无歌词」（`lyric_view.dart:149`），
   **不区分「确实没有」与「拿不到」**。

**推测（需真机或设备日志确认，按可能性排序）**
1. **`https://lrclib.net` 在该网络不可达**（境外服务，国内部分电视网络会超时/被拦）
   → `online.search()` 抛错 → 被 try/catch 静默忽略（:244 所在的 try）
   → 用户只看到「暂无歌词」。**这是最可能的原因。**
2. 该曲目在 LRCLIB 没有词条，或标题/歌手/专辑写法与库内差异大 → `score <= 0` 被丢弃。
3. 电视上该曲目**根本没有歌词面板可见**（被 3.2 的布局问题裁切），
   用户误判成「在线歌词没显示」。
4. `_music.getLyrics` 12s 超时（:191）在慢 NAS 上频繁触发 → 走在线；若在线也慢
   （9s 超时）→ 用户感知为「一直在转圈/没有歌词」。

**我无法提供的证据**：没有任何设备端日志（见第 7 节）。

### 5.2 播放控制栏遮挡内容

**已证实（读代码即可确认）**
1. 底部操作栏位于 `Column` 内部（`player_page.dart:205` 的 Column，底部栏 `:433`），
   **不是** `Stack` 叠加、**没有** `Positioned` 覆盖 → 结构上它不覆盖正文。
2. 正文是 `Expanded`（:208）→ 它的高度 = 剩余高度，**已经扣掉了底部栏与进度行**。
3. `_buildCoverPane`（:306）在 335 行构造一个 `Column`，372 行放规格胶囊
   `_Chip(song.audioSpec.display)`。这一块是**固有高度**（封面 + 标题 + 歌手 + 胶囊），
   不受可用高度约束。
4. Flutter 在 **release 构建下 `RenderFlex` 溢出是静默裁切**（不打日志、不画黄黑条纹，
   条纹只在 debug 出现）→ 一旦 3 的固有高度超过 2 给出的可用高度，
   表现就是**内容被切掉**，视觉上很像「被底部栏遮住」。

**推测（需要真机截图或 layout 断言才能定量确认）**
1. 电视常见逻辑视口是 **960×540**（1080p 面板 + density 2.0）。
   在 540 逻辑高里扣掉系统栏、顶部留白、进度行、底部栏之后，
   正文 `Expanded` 可能只剩 **300 上下**；而封面（`square` 由可用宽反推）+ 标题 +
   歌手 + 规格胶囊的固有高度很可能超过它 → 规格胶囊被裁。
   **这是我对本问题的首要判断，但具体超出的像素必须实测。**
2. `_buildStageLayout`（:249）用 `Row(Expanded(flex:5) / Expanded(flex:4))`，
   左栏宽度随视口变化 → 封面边长随之变化 → 溢出量是**动态的**，
   所以可能出现「720p 正常、1080p 出问题」这类不一致现象。

**建议的核对方向**（供第三方评估）：
把正文区改成「内容区 / 进度区 / 操作栏」三者**显式占位**（各自固定高度 + 弹性内容区），
并给弹性内容区加 `SingleChildScrollView` 或按可用高度自适应封面尺寸；
同时给出「内容固有高度 ≤ 可用高度」的可断言算式。

### 5.3 手机扫码连接不能用

**已证实（读代码即可确认）——以下四条都是**代码层**的真实可疑点，但都还没有真机证据**

1. **二维码静默区不足**：`qr_view.dart:14` `quietZoneModules = 2`，
   QR 规范要求 **≥4**。虽然外层白底容器有 10 逻辑 px 内边距（:26-31），
   折算后总静区约 3.75 个模块，仍**低于规范值**。
   → 静区不足是「扫不出来」的经典原因。
2. **`localIpv4()` 取地址的方式不可靠**：`remote_server.dart:233-249`
   取「第一个非回环 IPv4」，**不筛选接口类型**。
   Android TV 上常见同时存在 `wlan0` / `eth0` / `p2p0`（Wi-Fi Direct）/
   `dummy0` / VPN `tun0`，而 `NetworkInterface.list()` 的**顺序没有保证**。
   一旦取到 `p2p0` 或 VPN 地址，二维码里的 IP 手机**根本不可达**
   → 现象就是「扫码成功但打不开」。
   → 这条与用户的描述（「连接不能用」）**高度吻合**。
3. **配对码 5 分钟过期后二维码消失**：页面只在 `initState` 取一次码
   （`remote_control_page.dart:61-62`），`pairingCode` 过期后变 `null`，
   此时 `QrCode` 为 null（:109-111）、地址显示 `#------`（:105）。
   页面**不会自动重新生成**，需要用户手点「重新生成配对码」（:88）。
   → 用户停留超过 5 分钟再扫码，看到的就是「没有二维码 / 配对失败」。
4. **服务只在进入该页时才启动**（`app_shell.dart:339-352`），
   而**退出登录会 stop + revoke**（:521-522）。
   所以「上次能用、这次不能用」的常见情形是：期间登出/重登过。

**已排除（已证实不是原因）**
1. **不是 Android 网络配置拦的**：`AndroidManifest.xml` 已声明
   `android.permission.INTERNET`（第 6 行），且有 `usesCleartextTraffic="true"`；
   工程内**没有** `res/xml/network_security_config.xml`（已确认 `res/xml` 目录不存在），
   不存在「明文被策略拒绝」的可能。
2. **不是绑错地址**：监听的是 `InternetAddress.anyIPv4`（`remote_server.dart:255-259`），
   即所有 IPv4 接口，**不是** 127.0.0.1。
3. **不是二维码内容错**：内容为 `http://<host>:<port>/#<code>`
   （`remote_server.dart:757-762`）；绘制是**白底 + 黑模块**（`qr_view.dart:26-66`），
   不是白字黑底；掩码固定 0（`qr_code.dart:282`）与格式信息（:285 起）一致；
   纠错码字已用「码字多项式在生成多项式 20 个根上求值为 0」的单元测试校验过。

## 勘误二：二维码的结论完全错了

**正文原来写**：「二维码已排除错误：白底黑模块、掩码 0 与格式信息一致、

**实际**：手写编码器有**两处独立的实质错误**（详见 `lib/services/remote/qr_code.dart`

码字顺序、纠错校验子为 0、载荷解析）。

## 勘误三：「配对码过期后二维码消失」说法不准确

**正文原来写**：配对码过期后二维码消失、地址显示 `#------`。

**实际**（第三方核对得对）：`remote_control_page.dart` 在 `initState` 里把码复制到
`_code`，之后定时器只 `setState`，`build` 仍读 `_code` ——
所以过期后**不会消失**，而是**继续显示那个已经失效的码**，用户扫码后配对失败。

**处置**：改为在定时器里调 `pairing.refreshCode()`（只续期未使用的码、不撤销会话），
`build` 实时读取 `pairing.pairingCode`。这样过期会自动换新码，也不会把已连接的手机踢下线。

## 勘误四：「候选 UI 已存在」「手动选择已持久保存」都不成立
